# 连接配置修改与状态查询寿命

原生 Custom 地址字段已复现数据错配：请求发给第一个地址，用户改为第二个地址后，旧回复仍自动写入第一个地址的模型并宣称加载成功。记录见 `output/verification/status-cancellation-20261125/address-change-probe.log`。

连接检查属于开始时的配置。实际修改地址、协议、部署、区域、账户、认证方式或请求头后，旧检查应失效，不能回填模型、模板、上下文、状态或结束后续加载。保持同值的 input/change 不使检查失效。新的检查仍按现有显式连接或原预设重连规则发起；不自动选择其他协议，也不清空用户的模型配置。

主代理继续在 `feature/mobile-chat-shell` inline 完成。用户已授权日常修复及必要重构，无需例行方案审批；不提交、发布或操作另一会话使用的手机。

## 方案与职责

采用原 `script.js::cancelStatusCheck()`。OpenAI 模块在原生连接字段写入处比较实际值，改变时写入唯一的 `oai_settings`，随后取消原查询，让状态监听器读取新配置；请求头编辑在其自身所属的 parameters 对象写入处做同一处理。Text Completion 的既有地址绑定遍历遵循相同规则。只编辑另一个 provider 或 server 的记忆地址，不取消当前查询。代理预设的重连入口先取消，删除预设后选择的连接也经过共同的应用入口；删除最后一个预设不创建新预设。

已排除下游结果地址比对和额外版本号：它们让查询结果依赖第二套配置寿命判断，也不能覆盖准备密钥及代理确认阶段。字段变化由实际写入者发起，已修复的各查询继续遵循原信号。

## 验证与边界

复用 browser runtime、原生控件与真实 fetch interceptor，用确定性 I/O 验证地址修改前后两条查询、准备阶段、Text Completion 的实际地址绑定，以及请求头和代理预设入口。最高层行为覆盖放在独立 browser test 文件，避免继续增长已有接近 60 秒阈值的 API parent。

状态查询及生成 DTO、兼容路由、协议选择、手填模型和设置保存契约不变。请求体参数修改不属于模型列表连接变化；原生密钥管理继续由原持久化机制拥有。Rust 无改动。完整检查唯一已知环境问题是本机缺少 Xcode `actool`，仍执行并如实记录；手机验收待另一会话完成。

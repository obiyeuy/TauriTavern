# 请求失败的呈现归属

本项来自正式 APK 的真机复现：内置 API 短测试一次失败，界面同时出现三条通知，分别来自后端 CommandError 广播、Chat Completion 响应解析和测试按钮 catch。请求实际指向 `/v1/chat/completions`，失败为 `network.tls_failed`；手机 Chrome 对同域名也显示 `ERR_CONNECTION_CLOSED`。网络故障与重复通知分别处理。

用户持续目标已授权日常修复和必要重构，并明确不要求例行方案确认。本项延续当前分支和外部协议，不请求提交、推送、扩大凭据访问或改变网络设置。

方案采用调用者拥有返回错误：Rust 命令的 `CommandError` 继续原样返回并记录诊断；通过 Result 返回的错误不再触发全局产品事件。现有后台、部分成功和宿主错误仍显式使用 user-visible target。Chat Completion 的 quiet 请求将解析错误向调用者传播，由测试按钮或其他发起者决定呈现；正常聊天现有错误结果和公开 parser 的选项保留。

不采用按文案、时间或请求 ID 去重：三处文案不同，而且这会把重复职责留在系统中。也不把请求错误全部交给后端 toast：调用者拥有用途、语言和恢复操作，quiet 工具请求还可能无需界面通知。

验收须守住同一短测试只有一条错误、错误信息与拒绝仍可观察、普通命令诊断仍记录、预期取消／冲突继续使用 warn，以及显式后台错误仍通过原桥呈现。现有请求 URL、模型、密钥、配置存储、响应形状和事件协议保持。TLS 校验与 VPN 设置不改动；当前服务是否可生成仍需新的真实成功请求证明。

独立审阅确认，Quick Reply 保存／删除、背景上传、群组删除和表达图像删除曾依赖隐式后端通知。迁移同时检查第一方返回错误消费者：写入和删除失败必须在确认成功前停止后续状态变更，发起者呈现一次失败；供脚本调用的保存／删除入口继续返回可观察失败。Quick Reply 的延迟界面保存复用原 `performSave()`，由原 debounce 回调呈现失败并返回成功与否；API 的显式保存直接等待同一个写入函数，拒绝保留原错误，避免重复通知。HTTP 失败检查复用现有 command error 工具，与界面呈现分离。

复审确认遗漏包括普通头像、LAN 配对、Quick Reply 的新建／导入／复制、正则和预设保存、角色与群组的组合刷新及表情图片读取。新建与同名替换必须先写入，再发布到 registry；同名 Quick Reply 保留原对象及配置引用。预设保存拒绝时保留实际错误，界面只呈现一次；默认恢复不先删除旧预设。正则的列表调整暂存后保存，所有列表成功后才更新已应用标记；多份内容保存无法构成整体事务，失败须明确未能完整应用，保留可重试入口。角色与群组读取都成功后才发布组合结果。表情图片读取失败不能伪装为空列表或缓存；图库目录建议失败不阻塞主体，同时说明建议不可用。

# API 状态查询的取消与收尾

## 问题与证据

`cancelStatusCheck()` 取消并替换共享的 `abortStatusCheck`，但没有立即恢复连接按钮。OpenAI、Text Completion 和 NovelAI 的状态处理器在 `fetch` 因取消而拒绝后，仍会写入 `no_connection` 并调用 `resultCheckStatus()`。现有浏览器行为 harness 与真实 fetch interceptor 的确定性复现显示：三个入口都延迟恢复控件并覆盖了后续查询的状态。

Text Completion 后续 props 请求没有沿用取消信号。另一复现显示，已取消查询的旧 props 将模板标识改为旧模型，并将上下文长度从 65,536 改为 4,096。RED 记录在 `output/verification/status-cancellation-20261125/`。

独立审阅发现并复现两处同一生命周期的遗漏：准备密钥时取消，旧按钮操作恢复后重新开始查询；密钥准备失败则结束新的加载。旧反向代理确认被拒绝后也覆盖新状态并结束新加载。复现保留实际密钥失败提示，并让第二条真实查询保持等待以核对其控件状态。

全部共享控件调用者的自审还发现 Horde 的状态查询未传入共享信号；同一最高层用例复现旧 Horde 结果覆盖新状态、结束新加载。密钥写入守卫的 mutation 核对也证明：移除本轮写入后信号检查，会在三个连接入口重启旧请求；已将当前守卫精确恢复。

兼容性探测复现：取消信号缺少较新的 `throwIfAborted()` 时，原本成功的模型查询没有发布任何模型。本轮只用基础 `aborted` 属性判断查询寿命，订阅读取和 Horde 检查需要拒绝时使用 `AbortError`，不提高原有宿主 API 要求。已扩展现有模型加载用例覆盖该行为，没有另建重复测试。

fetch interceptor 已有请求与响应体的取消语义及行为覆盖，本次继续复用。原 404、服务端维护与手机网络问题各有独立证据，本次不将这些症状归因于本问题。

## 预期行为与职责

取消操作拥有当前查询的取消与控件恢复；每个异步查询持有开始时的同一个取消信号，取消之后不再发布状态、模型、订阅或派生模板，也不再结束新的加载展示。未取消查询的成功、错误及 bypass 行为保持既有语义。

`script.js` 继续拥有共享取消控制器与加载控件。三个 provider 模块从连接按钮入口捕获信号，密钥准备、状态请求、结果发布与控件收尾沿用同一查询寿命；独立密钥错误不吞掉。Horde 的自动状态入口沿用该信号，`checkHordeStatus()` 保留无参数调用行为，并允许该调用者传入信号。反向代理 validator 只验证传入的实际地址与取得确认，不负责状态和控件；状态查询与生成参数的两个调用者各自处理拒绝。Text Completion 的后续 props 请求与模板派生属于本次状态查询；NovelAI 的订阅读取供连接和图片额度入口共用，保留原无参数签名。

这属于用户已授权的稳定性修复。沿用现有上游 URL、响应、导出与事件契约，没有新的功能入口。

## 取舍与验证

实施调用者遵循现有取消机制的方案，不另设查询计数、当前状态副本或缓存，也不更改已有 fetch 取消机制。最高层行为覆盖应观察取消时按钮立即恢复、旧请求收尾后新状态保留，以及未取消查询正常完成。

运行 focused browser cases 与完整 `pnpm run check`，如实记录环境失败；未修改 Rust 时不机械重复独立 Rust 验证。手机按用户要求等待另一会话完成，本轮不以浏览器结果宣称真机验收完成。

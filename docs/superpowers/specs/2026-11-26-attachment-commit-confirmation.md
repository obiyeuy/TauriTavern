# 附件退役前确认替代引用

三个实际探针确认了附件提交链路中的问题：

- `/db-update` 上传并删除原件后，settings 写入返回失败；命令已经返回新 URL，磁盘仍引用被删原件。
- 角色附件上传等待时切换角色，新引用被发布到另一角色，原角色仍引用已经删除的原件。
- metadata integrity 冲突后，用户没有确认覆盖，原保存函数执行 reload 但正常返回；这种返回不能用作成功保存的依据。

编辑、移动和 `/db-update` 继续使用共同 `replaceAttachment()`。持久化目标的替代文件引用必须经原 settings／metadata 保存入口确认，之后才进入旧文件退役。保存等待和失败期间原文件、原引用与 disabled 保留；未确认时不返回替代 URL。已经上传的有效副本保留在原数据链路中，不通过回滚、状态镜像或自动删除唯一编辑内容来掩盖部分成功。

位置由已有 source 事实决定：global 不依赖当前角色；character 使用 avatar；chat 使用所属角色／群组、聊天名和 integrity。编辑在原件读取前捕获，移动在源操作和目标选择后捕获，抓取在采集前捕获，拖放在确认目标后捕获；这些位置作为同一个 uploader／替换函数的操作输入传递。在发起上传和发布引用时核对，替换还在读取／上传及保存前后核对 source／target 与原引用。位置改变时停止本次发布或退役，传播明确错误；已上传但未发布的文件通过错误中的实际 URL 保留可恢复信息。使用一个私有身份 getter，不增加宿主接口、配置、持久状态或第二份数据源。

拖放的真实回调接管拒绝，抓取控件等待原操作并保留原错误文本，不能丢失位置变化或已上传文件的路径。命令仍依原 executor 决定通知。原 helper 的可选位置输入是本次操作的目的地事实，省略时在调用处捕获，成功和失败结果形状不变。

settings 保存沿用 `flushPendingSettingsSave(true)` 的原布尔结果和通知 owner；metadata 保存取消同一 debounce 后等待原队列，原保存失败／integrity 提示拥有呈现。拒绝 integrity 覆盖仍 reload，并传播原错误，不能把拒绝当保存成功。替换中的已呈现 metadata 失败按原“没有新路径”的失败结果停止，避免再次弹出文件读取错误。

原文件路径、文件／引用字段、事件和成功 URL 不变，neutral chat 的 session 语义及 `saveMetadata()` no-op 不变，不计为磁盘 ACK。取消、无修改退出和三个实际调用者保持。此项不提供跨文件／settings 的原子事务，不保证旧引用清理的后续 debounce 或物理删除成功；这些原退役结果另有候选。

测试使用真实 Data Bank／slash／Popup、原保存器与合成 IO。守护保存期间原件、失败后的磁盘引用可读、正确 bucket、一次原因／事件、位置切换不误发布，以及成功重试。完成完整检查、逐路径自审和一次独立精确增量审阅；不使用手机、真实账户或业务文件。

# 支持转换的附件避免重复读取

当前选择器的私有文件政策已经统一。源码确认：对已注册 converter 的 MIME，binary 判断不影响允许结果，却仍先调用 `File.text()`；消息准备又先读整个 Data URL，随后转换器重新读取文件并完全替换这份 Base64。真实选择控件的本地探针使用 16 MiB、声明 `application/pdf` 的合成 File，五次选择都有全文读取，中位约 49.670 ms。该探针没有解析 PDF、上传、调用 provider 或操作手机；最终性能基线按上一项已收尾代码重新采集。

非媒体 size limit 仍先判断；媒体或已有 converter 的格式可根据元数据确认允许，不读取随后不参与判定的正文。未知格式仍使用原 binary 规则，且保留读取期间新增 converter 后可接受的既有行为。实际转换和传输读取仍拒绝原错误，不缓存文本、有效性或转换器结果。

`populateFileAttachment()` 在原校验和位置规则之后按实际输出选择读取：媒体和普通未转换文件继续原 Data URL／Base64 字节路径；转换文件只经原 converter 和 `convertTextToBase64()`。全部原文件字段、媒体分类、编码、上传路径、消息原子发布、部分副本恢复、位置／选择及错误 owner 契约保持。Data Bank 已经使用转换文本路径，仅共用元数据校验改进。

复用最高层附件 fixture，验证实际选择、准备和 Data Bank 的转换输出以及必要读取数量，保留现有失败／重试／位置覆盖。用相同数据与原控件测量选择和准备的前后读取次数、耗时；不声称手机启动或真实文档解码速度。实现完成运行 `pnpm run check`，准确记录环境失败并补足未执行的相关检查。一次精确四文件独立审阅，临时材料集中归档后清理，不提交、推送或操作手机／真实 provider。
